## Decisions

- **A `node:http` service with no framework**, so the request lifecycle (context, error boundary, access log, metrics) is visible in one file. It listens on `127.0.0.1:5808` by default and fails with one log line if the port is taken (no fallback port); `HOST=0.0.0.0` opens it to other hosts.
- **`GET /issues` and `GET /issues/:key` backed by the compose Postgres** (approved deviation): the load test then exercises the pool and the queries, and `/readyz` checks a dependency the service really uses. The seed is deterministic SQL mounted into `docker-entrypoint-initdb.d`; the healthcheck uses TCP (`pg_isready -h 127.0.0.1`) so `--wait` does not return while the init script still runs on the Unix socket.
- **The ~150-line limit applies per file** (approved): the largest solution file is `app.ts` with about 100 lines.
- **Correlation id with `AsyncLocalStorage` and pino's `mixin()`**, not child loggers passed around. Incoming ids are reused only if they match `^[\w.:-]{1,128}$`; otherwise a UUID is generated.
- **`runOutsideContext()` for pool errors** (addition found while running the service): an idle connection's `error` event fired in the context of the request that had opened the connection, so its log line carried an unrelated correlation id. The pool's listener now logs through `AsyncLocalStorage.exit()`, and two tests show the line with and without it.
- **A `DatabaseProbe` port, run with a timeout, through a separate single-connection pool** (the separate pool is an addition): under load the application pool is busy by design, and a probe queueing behind it would take healthy instances out of rotation. Readiness responses give check names and timings; error messages go only to the logs.
- **Draining on `SIGTERM`/`SIGINT` with `DRAIN_DELAY_MS`** (addition, default 0 locally): readiness fails, requests are still served for the delay, then the server closes and the pools end.
- **Sentry 11** in `instrument.ts`, loaded with `node --import` after `--import tsx`; `Sentry.init` only when `SENTRY_DSN` is set; `dataCollection` explicit (no user info, cookies, bodies, database values or local variables; allow-listed headers and query parameters); `captureException` with a `correlationId` tag. Tests cover only the DSN-unset path and the options; the full path was checked by hand with a local envelope sink (the event arrived with the tag and the transaction `GET /issues`). DSN placeholders use underscores (`replace_with_public_key`) because Sentry's DSN parser rejects dashes in the public key.
- **EMF written by hand** (`emf.ts`), one line per request on stdout and not through pino, so a log level never drops metrics. Dimensions `[["Service","Route"]]`; `Latency` (Milliseconds), `Requests` and `Errors` (Count, 5xx only, 0 rather than absent); status code, method and correlation id as properties; unmatched paths counted as `unmatched`. `emfProblems()` validates the structure and the limits (100 metrics, 30 dimensions).
- **Per-route alarms in CDK** (approved, because the emitted dimension set is `[Service, Route]`): p95 latency above 300 ms and `100 * errors / requests` above 1 %, 1-minute periods, 3 of 5 datapoints, missing data not breaching, alarm and OK actions to an SNS topic (the topic is an addition). A test checks that the alarms use exactly the dimension set the service emits; CloudFormation lists dimensions sorted by name, which CloudWatch ignores. Nothing is deployed.
- **`createPool()` in `src/lib/postgres.ts` makes every limit explicit** (`max`, `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout`, `query_timeout`) and requires an `onError` listener; its tests run against the compose Postgres, including a backend terminated with `pg_terminate_backend`.
- **Tests:** a Vitest `globalSetup` stops the run with "Start Postgres first: docker compose up -d --wait" when Postgres is down. The app is tested over real HTTP on a port chosen by the OS (`src/lib/local-server.ts`, the same helper as in api-integrations, copied because katas share no code) with stub repositories; the Postgres adapters and probes against the real database, a closed port and a TCP server that never answers.
- **k6 reads the script from stdin** (`docker run -i … grafana/k6:2.4.0 run -`), so nothing is mounted and Windows paths never reach Docker. `--add-host=host.docker.internal:host-gateway` as approved. On Docker Desktop (Windows) the service bound to `127.0.0.1` was reachable through `host.docker.internal`, so `HOST` keeps its loopback default; the README tells Linux users to set `HOST=0.0.0.0`.
- **k6 stages last 2m40s** so the real run fits a laptop; thresholds are the plan's two plus one p95 per route (`name` tags) and `checks: ['rate>0.99']`. `setup()` refuses to run against a service that is not ready, and `npm run load-test` checks `/readyz` from Node first. The run in `sample-output.md` is real (exit code 0) and is compared with the service's own EMF lines from the same run.
- **No `.problem` file for the k6 and incident exercises:** they are content exercises. The flawed load test and the flawed job loop are shown as excerpts in their statements; the k6 exercise is proven by the helper tests and the real run, the incident exercise by its documents.
- **The incident is fictional and documents only** (`scenario.md`, `communication-templates.md`, `postmortem.md`, `runbook.md`). Times are UTC; people appear only as roles. The AWS commands in the runbook are examples with placeholder names and are not executed; the freshness query runs against the kata's Postgres.
- **Scripts:** `check`, `test`, `start` (the service) and `load-test` (the k6 runner). `.env.example` holds the local defaults and an empty `SENTRY_DSN`; there are no secrets.
- **Branch base** (deviation): the worktree branch started from `main`, was fast-forwarded to `kata/ssr-fullstack`, and the series was rebased onto its latest tip whenever the coordinator added commits after that.

## Not verified

- ⚠️ Reaching a service bound to `127.0.0.1` through `host-gateway` on Docker Engine for Linux. The kata ran only on Docker Desktop for Windows, where it works; Docker's documentation of `host-gateway` does not cover loopback-only services: https://docs.docker.com/reference/cli/docker/container/run/
- ⚠️ Graceful shutdown with a real `SIGTERM`. Windows cannot deliver `SIGTERM` to a Node process from outside, so the drain sequence was checked by emitting the signal inside the process (readiness 503 with `draining`, requests still served during the delay, server closed, exit code 0): https://nodejs.org/api/process.html#signal-events
