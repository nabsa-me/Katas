## Decisions

- **Validators run in Docker through a Node script.** `src/lib/run-in-docker.ts` builds the `docker run` arguments as an array (tested): the kata folder (`process.cwd()`, which is the kata when run through npm) is mounted **read-only** at `/work`, so no validator can modify what it checks; npm runs scripts in `cmd.exe` on Windows, so nothing relies on `$PWD` or on a shell. `src/validate.ts` runs the checks registered in `src/exercises/index.ts`, one `validation.ts` per exercise.
- **A flawed file must report specific rule ids.** A check either expects exit code 0, or exit code 1 **and** listed rule ids in the output (`DL3007` for `Dockerfile.problem`): a wrong path also exits with 1 and would otherwise pass. The CLI checks that the Docker daemon answers before running anything, because the Docker CLI exits with 1 when it is down.
- **Policy tests next to the linters.** Linters prove that files are valid, not that they are production-ready, and the flawed Deployment and workflow are valid. Each exercise has a small pure module (`dockerfile-policy.ts`, `manifest-policy.ts`, `workflow-policy.ts`, `code-owners.ts`) whose tests show the findings of the `.problem` file and none for the solution. YAML is parsed with `yaml` 2.9.1 (YAML 1.2, so a workflow's `on:` key stays a string). The Dockerfile policy is an addition to the plan: hadolint only reports `latest` in the flawed file, not root, a single stage or dev dependencies.
- **`USER 1000:1000` instead of `USER node`.** hadolint 2.15.1 reports `USER node` with DL3066 (non-numeric user), and Kubernetes can only verify `runAsNonRoot` for a numeric user. 1000 is the `node` user of the official image (checked with `id node`), and the Deployment also sets `runAsUser: 1000`.
- **`Dockerfile.dockerignore` next to `Dockerfile`.** BuildKit reads `<Dockerfile name>.dockerignore` from the Dockerfile's folder before the context's `.dockerignore`, so the rules apply to the production Dockerfile only and `Dockerfile.problem` builds without any (as its statement requires). Checked by building with a temporary `app/.env`: absent from the production build stage, present in the flawed image.
- **Runtime files owned by root.** The runtime stage copies without `--chown`; only `.next/cache` belongs to the app user. The image also runs with `--read-only` and `tmpfs` for `/tmp` and `.next/cache` (checked), which the Kubernetes manifests mirror with `emptyDir` volumes.
- **`HOSTNAME=0.0.0.0` in the image and in the Deployment.** The standalone `server.js` listens on `process.env.HOSTNAME`; with Docker's default (the container host name) the loopback health check got `ECONNREFUSED` (reproduced). The Deployment sets it explicitly as well.
- **Measured, not estimated.** Both images were built on this machine and the README reports `docker image ls` values. Docker Engine 29 uses the containerd image store, which reports disk usage (compressed content plus unpacked layers) and content size (what a registry stores); both columns are given. `docker stop` timings and exit codes, the process tree of `npm start` and the `next start` warning are also measured.
- **Sample app dependencies are not installed locally.** `app/package-lock.json` was generated with `npm install --package-lock-only` and includes the Linux packages (`@next/swc-linux-x64-gnu`, `@img/sharp-linux-x64`); the app is type-checked by `next build` inside Docker and excluded from the kata's `tsc`. `next.config.ts` reuses `turbopack: { root: import.meta.dirname }` (Next.js also uses it as the file tracing root, so `server.js` is at the top of `.next/standalone`) and `agentRules: false`.
- **Deployment without `spec.replicas`, PDB `maxUnavailable: 1`.** The HPA owns the count (`minReplicas: 2`); a `replicas` field would reset it on every apply, and the consistency test reports it. `maxUnavailable` keeps working when the HPA changes the count.
- **kubeconform with `-ignore-missing-schemas`.** Only the ExternalSecret has no schema in the Kubernetes set; the summary reports it as the one skipped resource (7 valid, 1 skipped). Its `apiVersion` was checked against the External Secrets documentation instead. The tests check that the ExternalSecret and the example Secret produce the same Secret name and key.
- **Workflows assume the app at the repository root**, as they would be in the app's own repository, and live in `workflows/` inside the exercise; actionlint receives the files explicitly. The four deploy jobs are written out instead of calling a reusable workflow: a local reusable workflow must live in `.github/workflows/`, and four explicit jobs read top to bottom.
- **Deploy by image digest.** The build job exposes `registry/repository@sha256:…` from `docker/build-push-action`'s `digest` output and every environment deploys that value. Deploy jobs use per-environment variables (`AWS_DEPLOY_ROLE_ARN`, `EKS_CLUSTER`) and job-level `concurrency` with `cancel-in-progress: false`.
- **IAM documents.** `iam/trust-policy.json` is the prod deploy role's trust policy and `iam/deploy-permissions.json` its permissions (`eks:DescribeCluster` on one cluster); the build role's trust (`ref:refs/heads/main`) and ECR push permissions are shown in the README, as planned.
- **`code-owners.ts`, not `codeowners.ts`.** On a case-insensitive file system (Windows, macOS), the import `./codeowners` resolved to the `CODEOWNERS` file next to it and Vite tried to parse it as JavaScript.
- **Terraform write-only secret.** `aws_secretsmanager_secret_version.secret_string_wo` with an ephemeral, sensitive variable passed `terraform validate` with provider 6.74, so the kata uses it (the plan's condition). The master password is managed by RDS.
- **Terraform validation leaves nothing behind.** `TF_DATA_DIR=/tmp/terraform` keeps the downloaded provider inside the throwaway container and `-lockfile=readonly` installs exactly the committed lock file; the cost is downloading the AWS provider on every run (about 45 s). The lock file was generated once by `terraform init -backend=false` in the same image (linux_amd64 `h1:` hash plus the registry's `zh:` hashes for every platform).
- **Fictional identifiers.** AWS account ids are the documentation examples (`111122223333`, `444455556666`), subnets, security groups and the image digest are placeholders, GitHub owners are `ORG`, `REPO` and `@ORG/<team>`, and the only secret value is `replace-with-a-local-password`.
- **Port 5811** only for `docker run -p 5811:3000`; nothing else listens on a port.
