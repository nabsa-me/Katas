## Decisions

- **One Next.js 16 app (App Router under `src/app`) for the OIDC exercise; the API exercise is framework-free `node:http` run with `tsx`**, so the token checks are visible without a framework in between. Both share `rolesFromGroups` in `src/lib/roles.ts`.
- **openid-client 6.9.1, not Auth.js:** Auth.js v5 is still `5.0.0-beta.32`, while openid-client is stable, certified, and exposes each step the exercise is about (PKCE, `state`, `nonce`, the code exchange, the end-session URL).
- **Public client with PKCE S256, `state` and `nonce`.** `allowInsecureRequests` is added only when the issuer is `http:`, and the configuration accepts `http:` only for `localhost`, because the local mock has no TLS.
- **Mock provider:** `mock-oauth2-server` 7.0.2 on host port 5806 (container 8080), issuer id `katas`, interactive login, and a token callback that matches the typed username: `ada` gets `groups: ["katas-admins"]`, `grace` `groups: ["katas-readers"]`, plus `name`. The healthcheck uses the BusyBox `wget` that ships in the image.
- **`aud: ["katas-web", "katas-api"]` and `azp: "katas-web"` in the mock's mappings (addition approved on resume, `azp` added during implementation).** The mock puts the same claims in the ID token and the access token, and without `aud` in the mapping the access token has no audience at all. With two audiences, openid-client (oauth4webapi's `validateIdTokenAuthorizedParty`) rejects the ID token unless `azp` names the client, as OpenID Connect requires; `azp: "katas-web"` satisfies it.
- **Session:** a JWT signed with HS256 by `jose` in the `session` cookie (`httpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 8 hours) with `sub`, `name` and `roles`; the provider's tokens are discarded. The login transaction (`oidc_tx`: verifier, `state`, `nonce`, `returnTo`, 10 minutes) is signed the same way. Both carry distinct `typ` headers so one cannot be replayed as the other. `SESSION_SECRET` must be at least 32 characters and not the `.env.example` placeholder.
- **Configuration validated by hand, not with zod:** four variables, checked by `parseConfig`, which lists every problem at once. `src/instrumentation.ts` runs it at startup and calls `process.exit(1)` on failure, because Next.js 16.4.6 logs an error thrown in `register()` ("Failed to preload entries") and keeps serving 500s. `register()` does not run during `next build`, so the build needs no secrets. The `process.exit` lives in `config.ts` and is imported dynamically inside the `NEXT_RUNTIME === 'nodejs'` check, which keeps it out of the Edge build (otherwise Turbopack warns).
- **`proxy.ts` (Next.js 16 rename of `middleware.ts`)** with matcher `['/admin/:path*', '/api/admin/:path*']`: no session → 307 to `/api/auth/login?returnTo=…` for pages and 401 JSON for APIs; no admin role → 403. The 403 page uses `NextResponse.rewrite(new URL('/forbidden', request.url), { status: 403 })`, which keeps the status in Next.js 16.4.6 (checked with curl and by the Playwright test), so the fallback of answering HTML from the proxy was not needed. `forbidden()` is not used because it still requires `experimental.authInterrupts` (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/authInterrupts.md`).
- **Defense in depth:** `/api/admin/report` answers 401/403 itself, and `/admin` checks the role before rendering the data. A Server Component cannot set the status without `forbidden()`, so the page renders the forbidden message and the proxy provides the 403 status.
- **Logout is a POST form answered with 303 (approved on resume)** to the provider's end-session endpoint; `buildEndSessionUrl` adds `client_id` to `post_logout_redirect_uri`.
- **`returnTo` is restricted to same-origin paths** (`safeReturnTo`), so the login cannot be used as an open redirect.
- **The problem page reads its configuration after `await connection()`**, so it is rendered per request instead of being prerendered with build-time environment values.
- **TypeScript:** `next.config.ts` sets `typescript.tsconfigPath: 'tsconfig.app.json'`, because `tsconfig.json` only holds the project references. `next build` rewrites the tsconfig it uses, so `tsconfig.app.json` already contains what it adds (`plugins: [{ name: 'next' }]`, `allowJs`, `incremental`, `esModuleInterop`, `resolveJsonModule`, `.next/types` and `.next/dev/types` in `include`, `exclude: ['node_modules']`) and the build leaves it unchanged. `npm run check` works without a prior build or `next typegen`: importing from `next` loads its global declarations, including the one for CSS imports. `next-env.d.ts` is generated and ignored by the root `.gitignore`.
- **`next.config.ts` also sets `turbopack.root` to the kata folder** (the repository root has its own `package-lock.json`, and Turbopack otherwise warns and picks the outer folder) **and `agentRules: false`** (otherwise `next dev` writes an `AGENTS.md` into the folder when it detects a coding agent; documented in `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/agentRules.md`).
- **Playwright (approved on resume):** specs are `*.spec.ts` (Vitest only runs `*.test.ts`) and the script is `e2e`. `webServer` runs `npm run build && npm run start` (the production build, as the Next.js testing guide recommends) with its own local-only environment values, `reuseExistingServer: false` so a server already on port 5804 makes the run fail instead of being reused, one worker, and a `globalSetup` that fails fast with `docker compose up -d --wait` when the mock provider is down. Only Chromium is installed and tested.
- **`npm run token` (approved on resume):** submits the mock provider's login form without a browser, with PKCE, and prints the access token; `--unsigned` prints a forged `alg: none` token for the problem API. `npm run api -- --problem` runs the API with the flawed verifier.
- **API verifier:** `createRemoteJWKSet` + `jwtVerify` with `issuer`, `audience: 'katas-api'`, `algorithms: ['RS256']`, `requiredClaims: ['sub', 'exp']` and a 30-second clock tolerance. Only `jose` errors become 401 (`WWW-Authenticate` per RFC 6750); other failures become 500. The server takes `jwks_uri` from discovery after checking that the document's `issuer` matches.
- **Tests generate their keys:** `generateKeyPair('RS256', { extractable: true })` and a real `node:http` JWKS server on an ephemeral port; no keys or tokens in the repository. On algorithm confusion, the tests show that `jose` key sets refuse HS256 even without the allow-list (`ERR_JOSE_NOT_SUPPORTED`), and that a verifier handed the PEM bytes accepts it.
- **Line limit:** the ~150-line limit is applied per file, as in other katas of the series, because the OIDC solution has several concerns (configuration, session, flow, guard, return path) that the brief asks for together; no file reaches 150 lines.
- **Branch base:** the worktree was fast-forwarded to the tip of `kata/ssr-fullstack` before the first commit, so the series sits on top of the latest commits.
